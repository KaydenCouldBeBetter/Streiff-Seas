## Log row

| 2026-11-17 | **Interim: deploy a locally built bundle while GitHub is locked** (Kayden, during the M0-05b plan; **changes L3**). `deploy.sh` (M0-05b) does everything L3 asks: `deploy.sh <tag>` from a release and `deploy.sh --staging` from the newest green `ci.yml` build. Neither can run while the GitHub account is locked, since Actions builds nothing and there are no artifacts or releases to fetch. Until then, `scripts/make-bundle.sh` builds the same bundle on Kayden's machine, and `deploy.sh --bundle <dir>` (with `--staging` on staging) installs it. make-bundle refuses unless the tree is clean, HEAD is on `origin/main` and Node is the `.nvmrc` major. It then runs `npm run check` with `GITHUB_SHA` set and packs `bundles/<sha>/bundle.tar.gz` with `bundle.sha256`. Everything after the download is the same code as the GitHub modes: the sha256 check, the bundle's contents check, `FREEZE` and the live-tournament refusal on prod, the PocketBase pin, stop-copy-start backup, the symlink switch, the smoke test through Cloudflare, rollback and the deploy log. The order is: copy the bundle to staging (`pct push`), deploy it, check it on the phone, then copy **the same two files** to prod and deploy them there. **What this gives up, plainly:** (1) **prod no longer runs a build that CI tested.** It runs one built and checked on Kayden's machine, and no gate outside that machine has checked it. (2) The on-`main` check moves to build time, in make-bundle, where `deploy.sh` can't enforce it: the container has no git and no GitHub access to ask. (3) `bundle.sha256` travels with the bundle, so it proves the copy arrived intact, not who built it. Kayden compares the sha256 make-bundle printed with the one `deploy.sh` prints. | Kayden's call: the club's deadline is nearer than GitHub's return, and a deploy path that's the same as L3's from the download on is better than hand-installing files on prod | GitHub is back and M0-05a lands (then `--bundle` is for break-glass only, logged in `ops.md` §12, or it is removed) |

## Smaller M0-05b calls, recorded in the row's reasons if you want them in the log

- **Install layout** (Kayden, 2026-11-17): `/opt/scoreboard/{releases/<id>, current, pb_data, pb-cache}`, user `scoreboard`, unit `scoreboard.service`; `/etc/scoreboard/{ENVIRONMENT, FREEZE, deploy.env}`; `/var/backups/scoreboard/`; `/var/log/scoreboard/deploy.log`.
- **Live-tournament check** (Kayden, 2026-11-17): `sqlite3 -readonly pb_data/data.db`, refusing if it can't read; no superuser credential on the server (keeps the 2026-10-07 backup row's reasoning).
- **Order** (Claude's technical call, approved with the plan): deploy.sh downloads, verifies, unpacks and checks the PocketBase binary **before** stopping the service, then stops, backs up, switches, starts and smoke-tests. A bad bundle never causes downtime; the backup still comes before the switch.
- **`ENVIRONMENT` on prod too:** prod modes refuse unless `/etc/scoreboard/ENVIRONMENT` says `prod`, as `--staging` refuses unless it says `staging`, so neither runs on the wrong container.
