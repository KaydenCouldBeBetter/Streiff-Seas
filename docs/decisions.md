### L1. Identity and access (2026-10-01)

**Context.** The board is members-only for about 15 known people, and the server is PocketBase, which its own docs call not yet recommended for production-critical use. Cloudflare Access path rules can't protect API writes (a rule on `/submit` guards only an HTML page), so PocketBase's API rules are the only write gate that can be relied on.

**Decision.** Two independent layers, each of which must hold on its own:

1. **Cloudflare Access decides who reaches the server at all.**
   - One self-hosted app on the whole hostname, every path including `/api/*` and `/_/`.
   - Allow policy: **Include: Emails**, an explicit list matching the PocketBase users. Never `Everyone` or an email domain.
   - Login: one-time PIN to email. Session: 7 days.
   - No Bypass policies on any path of this hostname.
   - One service token, `uptime-probe`, for the 5-minute probe and the `deploy.sh` smoke test; it lives only in the prod LXC.
   - A second Access app on `/_/` allows only Kayden's email.
2. **PocketBase decides what a signed-in member may do.**
   - `users` sign in by OTP only; password and OAuth2 sign-in are off.
   - Users are created only by the superuser (`users` create rule `null`); `role` (`member` or `organizer`) changes only through the superuser.
   - Judging rights come per tournament from `events.judge` and `events.backup_judge`; nobody judges their own catch.
   - The superuser is a separate account with MFA, used break-glass only and logged (2026-09-30 entry).
   - Every rule is tested with Access absent (invariant 8).
3. **Same origin.** The React app is served from `pb_public/`, so the Access cookie works with no CORS setup.
4. **Membership changes.** Adding a member means adding them to the Access list and having the superuser create their PocketBase user. Removing a member means removing them from the Access list; their user and entries stay for history.

**Alternatives considered.**
- *Access only on `/_/`, PocketBase OTP as the only gate for members* (the guide's minimalist layout). Rejected while the board is members-only; it is the fallback if the club wants a public board at launch.
- *A public spectator board.* Out of MVP scope; it would get its own hostname and a verified-only list rule, never a Bypass on `/api/*`.

**Costs.** Two codes per sign-in (Access PIN, then PocketBase OTP), and each member uses one Access seat (free up to 50).

**Evidence.** X-ACC-01 to 05 in `docs/evidence/m0.txt`; R-USR-A-01 and A-02; every `L-01` row in `security.md`.

**What would reverse it.** The club wants a public board (separate hostname); membership passes 50; Access becomes unreliable in the soak test.

### L2. Photo pipeline (2026-10-01, pending the Phase 2 photo spike)

**Context.** PocketBase has no server-side way to strip EXIF or GPS, and its JS hooks run in an embedded engine with no image API. Fishing spots must never leak, but capture time is wanted as a flag. Photos are visible to every signed-in member, append-only on a pending catch, and archived after final.

**Decision: the pipeline, in order.**
1. **Client read.** The browser reads `DateTimeOriginal` from the original file before anything else and sends it as `captured_at`. It is a signal only (invariant 9).
2. **Client re-encode.** The browser resizes and re-encodes the photo to JPEG, which drops all metadata. This is a first line of defence, not the guarantee.
3. **Server strip or fail closed.** On catch create and on every added photo, the hook checks type and size, then either:
   - **A.** strips location with exiftool through `$os.cmd`; or
   - **B.** refuses any file that still carries location metadata (fail closed).
   Either way, no stored file or thumbnail ever contains location. A Go-extended PocketBase build was rejected because it breaks the prebuilt, pinned-binary pipeline.
4. **Protected multi-file storage.** `photo` is a protected file field holding 1 to 4 images, with a per-file size cap. It is append-only: the angler update hook refuses any request whose new list drops an existing file, checked before save so a refused request deletes nothing. Files load only with a short-lived token granted when the `catches` view rule passes.
5. **Archive.** After final and the post-finalize backup, `archive-event.sh` copies every photo of the event, with a sha256 manifest, to the Proxmox host and stops if any file has location metadata. The desktop pulls and verifies; only then are the photos removed from `pb_data`, outside the API. The laptop pulls on its next time on the home LAN. Encrypted B2 backups also hold them until retention expires.

**The Phase 2 spike decides.**
- Four fixtures (JPEG with GPS, JPEG with XMP GPS, iPhone HEIC, PNG with a text chunk), plus the same files sent as an added photo. Pass: neither the stored original nor any thumbnail contains location data.
- Option A or B for step 3, and whether exiftool can run in the LXC.
- That `DateTimeOriginal` is read before re-encoding on iPhone Safari and Android Chrome, and what each delivers for an iPhone HEIC.
- That the append-only check runs before PocketBase deletes a file on the pinned version.
The result is recorded as a new row in this log.

**What would reverse it.** Neither A nor B works on the pinned version (then a Go build, or client-only stripping with fail closed as the only server check); the append-only check can't run before deletion (then retract-and-resubmit only, and R-CAT-U-21 becomes Deny).
